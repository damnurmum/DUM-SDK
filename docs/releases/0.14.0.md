# DUM-SDK 0.14.0

Modules and cooperative Fabric mods now scope their effects to the accepted server session. This release also separates gameplay examples from the SDK repository.

## Changes since 0.13.0

- Require a compatible handshake, verified catalog, completed installation and play join before dispatching SDK callbacks. Old downloads and callbacks cannot activate a later connection.
- Add `DumServerMod` and the `dum-sdk:server` entrypoint for server-scoped Fabric mods, `ServerSession.active(modId)`, and context activity/cleanup APIs. Each connection gets a fresh context. A required cold mod failure disconnects the player and cleans up its registrations.
- Add session-scoped equipment appearance hooks for armor and wings, item model/name definitions for tagged vanilla carriers, and the Paper `ModuleItems` helper. These APIs do not add native registry entries or server gameplay.
- Publish staged module catalogs only through `/dumsdk reload`. Successful publication disconnects online players so everyone rejoins with the same catalog; restarting Paper retains the last published snapshot. Invalid staging cannot replace it.
- Enforce module message ownership, operator-only catalog filtering and per-player/module rate limits on the server.
- Remove bundled `info`, `sdktest`, `dumcoldtest` and the accessories gameplay implementation. Examples and their test fixtures are maintained outside this SDK repository.

## Upgrade notes

Update the Fabric SDK and Paper plugin together. The client download is `DUM-SDK.jar`; the Paper artifact is `DUM-SDK-Paper-0.14.0.jar` and requires the private DUM-Core dependency.

Servers using the previous bundled accessories must install their separate `DUM-Info` plugin and keep publishing the `info` client module. The extracted implementation preserves the original player data keys. Example/test binaries are not bundled in this release.

Cold mods must migrate to exactly one `dum-sdk:server` entrypoint implementing `DumServerMod`, depend on SDK 0.14.0 or newer, and avoid ordinary startup entrypoints. Replace legacy jars in both staging and the active published catalog before upgrading Paper; a catalog containing legacy cold jars fails validation. Rebuild/migrate clients' legacy cold mods before testing.

Every permanent mixin must guard its behavior with `ServerSession.active(modId)`. Use the session context for managed handlers and cleanup; arbitrary Fabric mods are not automatically isolated. Classes, mixins, native registry entries and native Fabric assets remain loaded until the JVM exits. Native registry content and cross-server compatibility need separate validation.

## Validation

- Local macOS build, unit tests and game-test compilation, including the Paper project.
- Real client/Paper tests for handshake, tagged item presentation, equipment callbacks, optional module failure, reconnect and transition to a server without plugins.
- Real cold fixture installation through the restart helper, title mixin activation only for its accepted catalog, fresh/expired contexts, cleanup, transition to another SDK server without the mod, a plain server and singleplayer, and required cold mod failure.
- Windows/Linux checks for the new session APIs, Sodium/Iris compatibility, visual equipment/model inspection and a real cold mod with native registry content remain unchecked. See `CHECKLIST.md` for historical test build labels and details.
